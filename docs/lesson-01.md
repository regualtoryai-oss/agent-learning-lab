# 第一课：沿源码追踪一次完整 Agent 任务

目标：理解一次任务从输入到交付经过哪些模块，模型选择动作后由谁执行，执行结果怎样影响下一轮，以及怎样确认任务真的完成。首场用 **90–110 分钟**，以 DSH 完整任务链为主线，对照 Codex harness 的少数相同职责，再观察一次运行。

阅读位置与固定版本见 [DSH / Codex 源码学习指南](source-study.md)。本课使用官方 DSH 基线 `5badb15009ae1756c3afe0ae0cef1faafc290ccc`、Codex 基线 `315f0efb34880e44b642208b4b2cb289760c7ca1`。只读源码，在学习项目中独立实现后续增量。

## 今天追踪的任务

选择一个小的资料任务，例如“阅读指定教学文档，给出三条结论并标明依据”。先写清输入、允许读取的资料、期望交付物和完成标准。沿同一个任务查看完整路径，不逐个函数孤立阅读。

```text
用户输入 → 组装指令、工具与上下文 → 请求模型
                                      ↓
                             模型给出工具调用
                                      ↓
                         分发、校验、执行与记录结果
                                      ↓
                         将结果送回下一轮模型上下文
                                      ↓
                         继续行动或交付结果并结束
```

这张图是阅读导航，具体是否继续、怎样持久化与怎样结束，以对应版本的源码和运行证据为准。

## 首场安排：约 100 分钟

| 时间 | 行动 | 留下什么 |
| --- | --- | --- |
| 10 分钟 | 确定一个小任务及可检查的完成标准 | 输入、资料范围、交付物与验收项 |
| 25 分钟 | 在 DSH 中沿输入、上下文组装、模型输出、工具执行、结果回写和结束判断阅读 | 带源码位置的流程图；每个模块用一句话说明职责 |
| 15 分钟 | 在 Codex 中对照工具分发、结果回写、继续或结束三个职责 | 三项有限对照：同一问题如何处理，哪些选择与当前项目有关 |
| 25 分钟 | 观察一次可运行环境的任务；在本仓库也可使用已有 Mock 演示核对事件 | 一份标明运行方式的轨迹，逐段对应到源码职责 |
| 15 分钟 | 检查工具结果、最终交付物及结束原因是否符合任务标准；标出一个待验证问题 | 一份验收记录，清楚写明观察到什么、仍不能证明什么 |
| 10 分钟 | 用流程图和轨迹讲解完整任务，整理下一项实现增量 | 简短讲解和下一步的一个小改动 |

导师负责源码导航与概念解释，学习者负责整理自己的流程图、核对观察结果并说明设计选择。讲解围绕完整任务与工程取舍展开。

## 观察时怎样记录

先确认运行来源，三类证据分开保存：

- **源码推演**：根据代码推断可能路径，没有实际执行；不得填写成真实日志。
- **Mock 轨迹**：程序实际执行，但模型行为来自固定脚本，只能核对该场景的控制流。
- **真实模型轨迹**：实际使用已配置模型，记录输入、工具结果、最终结果和运行条件；一次成功仍不能证明稳定完成任意任务。

本仓库默认演示已有正常、工具错误和超限场景：

```sh
npm run demo
npm run demo -- --scenario=tool-error
npm run demo -- --scenario=limit
```

默认 Mock 不理解任意提问。上面的日志可以用来观察执行链，但不能冒充“阅读任意资料并正确回答”的真实模型验证。若尚无可运行的 DSH 环境，可以保留 DSH 源码推演，并使用本仓库 Mock 核对共同的模块职责；无法观察的部分列为待验证。

已有真实模型 adapter 的使用条件见 [README](../README.md#可选真实模型)。具备配置和使用条件后，再取得真实模型运行记录；没有取得时如实保留待完成项，不编造调用和质量结果。

轨迹至少记录任务输入、模型选择的动作、工具实际收到的参数、工具返回、结果怎样进入下一轮、结束原因和最终交付物。工具执行成功、执行器 `completed` 与业务目标达成分别核对，不能用最后一句回复替代验收。

## 本课成果与下一步

完成本课应留下：一张有源码位置的流程图、三项 Codex 对照、一份标明来源的观察记录，以及一个能依据证据说明的设计取舍。尚未实际运行的环节必须标明。

本周继续建立 **5 个固定任务**，覆盖普通回答、资料缺失、证据冲突、工具错误及预算或取消边界；根据实际资料构造案例。真实模型基线未运行时，不能把 Mock 结果记作模型任务成功率。

随后从观察中选一个小模块独立实现或扩展，例如工具异步执行、会话检查点，或缺失的轨迹字段。仓库已有 HTTP、SQLite、trace 和取消时，先验证它们的边界，再决定增量，避免重复搭建。保留修改前后的任务记录，解释改动解决了什么问题。
