# 10 周：沿真实源码完善一个 Agent 作品

更新日期：2026-10-05。每周 **6 小时必修 + 2 小时选修**，总计 60–80 小时。以 DSH 的完整任务链为源码主线，对照 Codex harness，在本仓库独立实现小模块，逐步完成一个带引用的资料研究 Agent 应用。

岗位要求与课程取舍见 [JD 对齐说明](jd-alignment-2026-10-05.md)；固定源码版本与阅读位置见 [DSH / Codex 源码学习指南](source-study.md)。这些是学习安排，不代表功能已经完成或已经满足岗位要求。

## 起点与学习方式

本仓库已有 CLI、只读工具、轮数与时间预算、取消、事件 trace、localhost HTTP、SQLite 持久化及 22 项离线测试。课程会验证并扩展这些能力。默认 Mock 是固定脚本；真实模型 adapter 已提供，但目前没有真实模型运行记录。真实认证、执行恢复、向量检索和 RAG 评测仍待实现或验证，详见 [README](../README.md)。

每周安排：**1 小时源码与设计、3 小时实现、1 小时验证、1 小时记录与讲解**。先沿一个完整任务理解模块职责，再选择一个小改动，固定验收任务比较前后结果。只读上游源码；实现放在本仓库，不修改定制 DSH。

TS / Vue 是核心技术栈。额外 2 小时可用于更复杂的失败案例，或选择 **Python / FastAPI 与 MCP 中的一项**做薄桥接：前者验证一个服务接口，后者接入一个工具接口。无需在主课程里重写整个后端或同时学习多套 Agent 框架。Go、K8s、平台调度、多 Agent 和自进化留作进阶方向。

## 每周成果

| 周次 | 源码问题与作品增量 | 可验证成果 |
| --- | --- | --- |
| 1 | 沿 DSH 追踪输入、上下文、模型、工具、结果回写和结束；对照 Codex 相同职责。观察现有执行器，建立 5 个固定任务 | 有源码位置的任务流程图、一份标明运行方式的轨迹、5 个任务的验收标准。条件具备时完成真实模型基线；只有 Mock 时明确真实模型基线待完成 |
| 2 | 理解模型如何选择工具、运行时如何校验与执行；扩展已有工具契约与异步执行 | 正常结果、参数错误、超时三条路径；说明错误是否重试、交给模型调整或结束任务，并核对结果是否实际写回上下文 |
| 3 | 区分模型上下文、持久化会话和执行进度；从现有中断标记扩展检查点与恢复 | 一项中断任务能按明确策略恢复；记录恢复前后状态，以及哪些副作用不能直接重放。原有“重启后能查历史”不能充当执行恢复证据 |
| 4 | 理解检索结果如何进入上下文；建立带出处的资料检索与回答链 | 在小规模公开或合成资料上记录查询、命中文档、引用位置和最终结论；包含资料缺失、证据冲突或检索相关但不能支持结论的案例。先测关键词基线，再按证据决定是否引入 embedding |
| 5 | 理解评测如何定位模型、检索、工具和运行时的不同失败；扩展至 15–20 个固定任务 | 可重跑的小样本评测记录，包含任务结果、引用与缺口处理、工具错误等实际验收项；完成一次有前后结果的改进，区分用于调试的案例和保留的回归案例 |
| 6 | 从现有 HTTP / SQLite 服务连接 Vue，验证任务生命周期与界面反馈 | 可发起任务、看进度、查结果并取消；验证流式或事件更新与持久化结果的一致性。教学身份请求头的局限写清楚；真实认证如未完成，继续保持本地演示范围 |
| 7 | 理解重试、重复执行和业务副作用；扩展已有预算与取消机制 | 一次可重试错误、一次必须停止的错误、一次重复写入保护；有有限重试次数、总预算和幂等依据，能解释取消后的结果如何处理 |
| 8 | 沿源码观察执行轨迹与权限边界；扩展已有 trace 和白名单 | 每次运行能定位模型与工具阶段、耗时和失败原因；模型实际提供使用量时记录 token，并注明成本估算依据。加入可验证的目录或资源限制、写操作审批，避免将提示词当成权限保证 |
| 9 | 把依赖、配置与运行条件变成可复现交付；核对部署边界 | README、示例配置、Docker 或清晰本地启动流程；在干净环境运行 Demo。默认使用合成资料或公开资料，不将未完成认证的服务直接开放公网 |
| 10 | 用固定业务验收解释设计取舍，扩充至 20–30 个任务，整理作品集与面试演示 | 3 分钟演示、架构说明、评测结果、已知局限、一页“需求 → 设计 → 结果”案例；能依据代码和运行记录解释一次成功、一次失败和一次改进 |

## 怎样判断进步

评测从第 1 周开始，第 5 周集中扩充和分析。5 个起始任务至少覆盖普通资料回答、关键资料缺失、证据冲突、工具错误和预算或取消边界；按实际材料与工具构造，不为凑类别捏造内容。20–30 个案例是项目内的小样本，结果不能直接推广为生产成功率。

业务验收应检查结论与引用是否对应、缺口是否明确、必要约束是否满足、失败是否留下可排查信息。运行状态为 `completed` 只说明执行器结束，仍需检查交付物。只在任务完成标准要求时加入人工确认；可预先确定的步骤可以采用固定工作流。

每周用 [学习记录模板](learning-log-template.md) 保存一项设计选择、一次运行证据和一个已知限制；讲解计入当周记录时间。明确区分 **源码推演、实际执行的 Mock 轨迹、真实模型轨迹**，并标明 AI 协助与自己完成的部分。学习作品可以证明具体实现与验证过程，不能写成生产经验。
