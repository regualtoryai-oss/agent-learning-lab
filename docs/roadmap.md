# 10 周：用 AI 辅助交付一个 Agent 应用

更新日期：2026-10-05。每周 **6 小时核心练习 + 2 小时选修**，总计 60–80 小时。主目标是 Agent 应用研发 / AI 全栈，补充需求拆解与交付能力。以 TS / Node.js / Vue 为主，围绕同一个带引用的资料助手积累面试可展示的证据。

岗位依据与课程取舍见 [JD 对齐说明](jd-alignment-2026-10-05.md)，作品如何证明能力见 [岗位能力与面试证据](job-readiness.md)。以下是学习安排和待执行的验收项，不代表功能已经完成、学习者已经掌握或已经满足岗位条件。

## 学习方式与现有起点

每课按 **工作问题 → 必要概念 → AI 辅助实现 → 实际验证 → 讲解取舍** 进行。可以让 AI 生成代码、解释报错和提出方案；学习者需要能判断方案是否适合需求、定位失败发生在哪个环节，并用实际结果核对改动是否有效。课程不要求关闭 AI 编码、手写完整 loop 或逐个阅读上游函数。

本仓库已有 CLI、只读工具、轮数与时间预算、取消、事件 trace、localhost HTTP、SQLite 持久化及 22 项离线测试，可直接复用。默认 Mock 是固定脚本，真实模型 adapter 尚无真实运行记录；真实认证、执行恢复、向量检索和 RAG 评测仍待实现或验证。已有 HTTP 服务也需要核对并接入实际模型运行路径，不能把 Mock 服务视为已完成的真实模型后端。当前 CLI 使用执行器默认的 5 秒总预算，真实调试时应核对并调整，不把超时误判成模型不会使用工具。具体边界见 [README](../README.md)。

每周核心时间建议分配为：**0.5 小时理解问题与概念、3 小时实现、1.5 小时验证、1 小时记录与讲解**。资料使用自编材料或适合使用的公开资料，不导入私人知识库与真实业务数据。

额外 2 小时可用于失败案例，或选择 **Python / FastAPI 与 MCP 中的一项**做小型扩展。DSH 与 Codex harness 用于理解工作机制、比较设计选择；遇到具体问题时按需查 [设计与源码参考](source-study.md)，源码位置是选修阅读导航。Go、K8s、平台调度和多 Agent 作为岗位分支，不塞进同一条主课程。

## 每周成果

| 周次 | 工作问题与作品增量 | 待验证的成果 |
| --- | --- | --- |
| 1 | 资料助手怎样从问题到工具调用再到有依据的回答？复用 adapter 和只读工具，建立真实模型基线 | 实际模型读取教学资料并回答；记录调用、结果与引用；建立 5 个固定验收任务。配置未具备时明确列为待完成，不用 Mock 代替真实模型基线 |
| 2 | 模型怎样调用业务接口，应用怎样处理异步 I/O？将实际模型路径接到现有 Node 服务，接入一个资料查询接口 | 正常、接口超时与结构化错误有真实记录；明确哪些错误可重试、可让模型调整或必须停止；接口结果实际进入后续决策 |
| 3 | 连续提问需要保留什么？中断后怎样继续？区分上下文、历史与执行进度，为只读任务加入简单检查点 | 多轮问题能引用先前资料；一项中断任务按明确策略恢复；证明“查询历史”和“恢复执行”的不同，不直接重放有副作用的步骤 |
| 4 | 检索到相关资料，为什么仍可能答错？扩充小型语料，建立检索、引用与缺口处理 | 结论可以对应到实际读过的文档与证据位置；包含缺资料、证据冲突和相关但不能支持结论的情况；先测关键词基线，再按结果决定是否加入 embedding |
| 5 | 怎样证明改动让应用变好？扩充到 15–20 个固定案例，区分检索、模型、工具与运行时失败 | 一份可重跑的小样本评测；完成一次有前后结果的改进；记录验收失败原因，保留一组未用于调参的回归案例 |
| 6 | 用户怎样使用这个助手并看懂当前进度？用 Vue 连接现有 HTTP / SQLite | 可发起、查询、取消任务并查看资料依据；通过轮询或事件更新展示进度；刷新页面后可查持久化结果，取消与结束状态一致。真实认证未完成时保持本地演示范围 |
| 7 | 怎样防止重复操作和无限尝试？为保存报告等写动作设计审批、幂等、有限重试和预算 | 一次可重试错误、一次必须停止的错误、一项重复写入保护和一次审批过程；检查取消后的结果。权限由程序验证，不能只依赖提示词 |
| 8 | 一次任务为什么慢、贵或失败？完善模型与工具阶段的 trace | 可定位耗时和失败阶段；模型实际提供使用量时记录 token，说明成本估算依据；比较一次改动前后的结果和耗时。缺失的指标标为未测 |
| 9 | 别人怎样复现这个作品？整理配置、启动、数据与交付边界 | 示例配置、演示资料、Docker 或清楚的本地启动步骤；在干净环境运行 Demo；说明认证、数据权限和部署限制，不直接将未完成认证的教学服务开放公网 |
| 10 | 面试中怎样说明自己做了什么、为何这样设计？整理演示与变式练习 | 3 分钟演示、架构说明、评测结果、失败复盘与已知局限；用一个需求变化做小改动并验证；依据实际记录解释一次成功、一次失败和一次改进 |

## 怎样判断能力提升

面试证据围绕六项工作能力积累：需求与验收、模型与工具集成、上下文与资料检索、前后端交付、评测与排障、运行治理。每项都对应具体实现和运行记录，不能仅用术语解释或 AI 生成的代码证明掌握。

评测从第 1 周开始，第 5 周集中扩充。5 个起始任务可覆盖正常资料回答、关键资料缺失、错误前提或证据冲突、工具错误、预算或取消；按实际材料与工具构造，不为凑类别编造内容。后续案例数量按实际时间扩充，项目内的小样本结果不能直接推广为生产成功率。

业务验收检查结论与引用是否对应、缺口是否明确、必要约束是否满足、失败是否留下可排查的信息。**completed** 说明执行器结束，仍需检查交付物。可预先确定的步骤可以采用固定工作流；只在确有动态决策需求时增加 Agent 自主选择。

每周用 [学习记录模板](learning-log-template.md) 保存一项设计选择、一次实际证据和一个已知限制。第一课可先写四行简短记录。真实模型运行、Mock 测试和源码推演应明确标注；记录 AI 提供了哪些帮助，以及自己核验了什么。学习作品证明具体实现与验证过程，不能写成未经证实的生产经验。
